# Independent static audit — boundary certificate and baseline trust chain

## Scope and result

Audited `/root/erdos-302-independent-audit/source/erdos302_boundary_certificates` as an untrusted, non-git source snapshot. Line references below are relative to that directory. No uploaded Python, Lean, shell, tests, or binaries were executed; no source file was modified. System `sha256sum` and independently written Python standard-library arithmetic were used on data only. Uploaded logs are historical assertions, not execution evidence. This is not a proof of the Erdős bound and is not a Lean kernel verification.

**Bottom line:** the deliverable is not an end-to-end verified Lean proof. The local checker has substantial exact finite checks, but the global baseline depends on external profile theorems and on an unformalized mathematical bridge. Its own generated Lean only states finite conditional Boolean obligations and is explicitly uncompiled. Several input/provenance and execution trust boundaries need hardening before accepting an untrusted bundle.

## Release / mathematical blockers

1. **No checked Lean theorem of the actual extremal problem.** `lean/BoundaryCertificates.lean:1-5,14-25` shows finite arithmetic and Boolean implications, not an f302 or global-density theorem; `generate_lean.py:26-35,37-54` emits only those obligations. `LEAN_HANDOFF.md:5-8,29-48,59-66` explicitly says Lean was not compiled and calls out the missing semantic bridge. `baseline/LEAN_HANDOFF.md:7-14,24-38` calls for, rather than supplies, the all-N bound and kernel proof. **Action:** formalize the exact reciprocal-triple-free extremal function, the cover correspondence, completeness of edge enumeration, finite checker soundness, all projection/renewal/counting steps and exact arithmetic; build at a pinned Lean/Mathlib revision, inspect the precise final theorem type and transitive `#print axioms`, and reject `sorryAx`, unapproved axioms or unexplained premises. Include negative mutations. No Lean toolchain build or axiom check was performed in this audit.

2. **External profile data are trusted premises, not authenticated theorem applications.** `baseline/verify.py:14-19,49-59` checks hard-coded digests, a JSON commit label and a scalar aggregate, then `:84-90,125-128` turns the reconstructed profile into `externalActive` cover demands; `:218-243` also inserts all old profile values into renewal. A checksum or equality of aggregate rationals does not prove every per-level interval is the intended theorem nor that the pinned external theorem establishes it. `baseline/PROOF.md:24-39,125-140` acknowledges the external dependence; `baseline/LEAN_HANDOFF.md:35-38` requests four externalActive and 20 profile inputs as proof terms. `verify_all.py:27-41` inherits this dependency. **Action:** obtain the actual external repository at the stated immutable commit, verify its toolchain and build, identify exact theorem names/types/axioms, prove the translation of each interval and prefix into the local profile semantics, and bind these proof terms into the final theorem. Until then the baseline's mathematical claim is conditional, irrespective of matching hash files or reported statuses.

3. **Global bridge is a written argument, not a checked proof.** `baseline/PROOF.md:93-123` describes parity projection and extension coverage, `:125-156` renewal, and `:158-194` smooth/rough blocks, inclusion-exclusion error and transfer to f(N). `baseline/verify.py:218-257` calculates corresponding tables and rational quantities; it cannot by itself prove those general lemmas. In particular, matching a finite ledger does not establish the all-N recurrence or its relation to the original problem. **Action:** independently review and formalize each lemma, including positivity/injectivity of dilation, primality/order, full edge completeness, zero-correction tail, disjointness and finite error; separately check actual source theorem statements and transitive assumptions. Do not present the numerical replay as kernel proof.

## Untrusted-input and operational attack paths

4. **Generated Lean source injection through certificate identifiers (confirmed static path; conditional on attacker-controlled certificate and later generation/compilation).** `verify_boundary.py:98-105,111-115,154-159,180-183` accepts arbitrary unique strings for gate, table, and row identifiers without Lean identifier validation. `generate_lean.py:37-45,46-54` interpolates table/row IDs into declarations and `#print axioms` as raw source. A malicious ID containing newline and Lean command syntax can change the emitted program if the rest of the certificate and references are made consistent. Lean elaboration supports commands beyond theorem declarations; compiling arbitrary generated source is not a safe data-only check. The supplied identifiers have not been shown malicious, and no payload was run. **Action:** encode IDs into a strictly limited, injective identifier alphabet or use generated numeric identifiers with a separate escaped mapping; reject line breaks and syntax, test malicious IDs, and compile only in a resource-limited isolated environment without secrets/network or writable sensitive mounts. Review generated source before build.

5. **Hash manifest is not a trust anchor and does not constrain code loading.** `verify_all.py:16-23` reads the bundle-controlled `baseline/SHA256SUMS` without pinning its digest, required entries or a nonempty set; an empty manifest produces count zero. `:12-14,25-30` then imports and executes `baseline/verify.py` and `verify_boundary.py`; the latter is not covered by that baseline manifest. Anyone able to replace the bundle can replace the manifest and code together, omit entries or supply an empty manifest; the loader executes the resulting modules. This is a code-execution exposure only when a recipient runs the untrusted checker, not evidence that these supplied files are malicious. `verify_boundary.py:90-96` validates the claim hash but never compares `archive_name` or `archive_sha256` against archive bytes; `MANIFEST.json:4-12` gives two archive digests, but the named archives are not in the audited directory. **Action:** independently authenticate an externally distributed signed digest for the complete release, pin an exact nonempty path set and protect the manifest itself; separately obtain and hash the referenced archives and map their contents to this snapshot. Do not import or execute checker code from an untrusted archive on the host.

6. **Success can be vacuous for a replacement boundary certificate.** `verify_boundary.py:85-96` checks root field names and baseline metadata, then `:98,111,155,180,222,254` iterates lists without requiring nonempty lists or specified expected IDs/counts; `:267-275` returns a success status and counts even if all lists are empty. `verify_all.py:30-35` can then add no boundary rows, so baseline replay does not by itself establish that the intended boundary certificate was present. This is an arbitrary-input/acceptance-policy issue, not a claim that the frozen `certificate.json` is empty. **Action:** bind an externally authenticated certificate digest or require the specific expected IDs and counts and independently check the desired theorem statements; add empty/missing/replaced certificate negative tests. Do not infer a meaningful theorem merely from a status string.

7. **Unbounded work and report overwrite risks on attacker-controlled input.** `verify_boundary.py:39,43-46,117,254-257` limits file size and support size, not magnitude of vertex integers or number of rows; `baseline/verify.py:23-33,89-90,101-105,129-159,180-184` has bounded xz expansion but no comprehensive complexity, plain-JSON byte, tree-expansion, or numeric magnitude limits. Repeated tree branches, giant integers, and large node collections can exhaust CPU/memory; `baseline/verify.py:180-184` indexes `source_node` before validating it at :203-205. `verify_boundary.py:279-287`, `baseline/verify.py:263-264,280` and `verify_all.py:25-26,52` permit caller-selected `--report` paths, overwriting an existing file. These are deployment hazards, not established proof unsoundness; malformed data may just fail closed. **Action:** impose total node/edge/tree-visit/bit-length/input-size budgets before heavy work, enforce time/memory limits outside the process, validate indices before use, and write reports to exclusive output paths in a disposable sandbox.

## Integrity and independent arithmetic observations

- `sha256sum -c SHA256SUMS` passed all **69** top-level listed paths; running it from `baseline/` passed all **27** baseline listed paths. No missing files or hash mismatches. Each manifest has unique path entries and covers every regular file in its tree except itself; the parent manifest covers `baseline/SHA256SUMS`. Observed SHA-256 of top manifest: `e08a2313662cbb418d4731488e91d3ef54ae355bbd3e8b8802353d22b330dba8`; baseline manifest: `ce3d5e943f3498ba642cad9004ec5ed8ff3ad778504afea962b752600cd677b9`. These are local fingerprints, not externally authenticated origin evidence; no archive hash was verified.
- An independently written short data-only rational calculation from `baseline/VERIFIED_REPORT.json` checked 20 level `rho` values and correction integrals, totaling 4,705 recorded cells. It reproduced the report and `claim.json` exact upper rational, reproduced finite error **55,064,831,540**, and confirmed the rational is strictly below the stated headline. This checks ledger arithmetic only: not validity, completeness, provenance, sorted/disjointness of every cell, the 500,000-entry profile tables, the bank, or theorem transfer.
- Positive static controls: duplicate JSON fields rejected in both accepting readers (`verify_boundary.py:32-40`; `baseline/verify.py:23-33`); strict integer checks exclude booleans for most numeric inputs; finite tables regenerate reciprocal edges and exhaustively check state costs and witnesses (`verify_boundary.py:50-64,111-145`); derived sums require positive weights and rounding checks capacities (`:180-215`); every emitted inequality is separately rechecked over direct covers (`:251-261`). Baseline bank references are backward-only, and small covers/weighted and case rules have explicit checks (`baseline/verify.py:92-121,129-161`). These controls are static observations, not executed verification.
- `baseline/crosscheck.py:5-9` imports the main verifier and `:12,23-24,28-44` uses its routines or its report; its edge/ledger paths are alternate algorithms, not a fully independent trust chain. `crosscheck_boundary.py:37-67` separately handles boundary states and strict examples, not all derived rules or global proof. Historical logs do not change this scope.
