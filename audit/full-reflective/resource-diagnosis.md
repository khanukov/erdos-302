# Hosted thread-creation failures: candidate experiment

Evidence: GitHub Actions runs 41386482727 (job 125088341868) and 41386480346 (job 125088355629), both at 1fd2ae2acdcef7c4967fef158187fefed7aba130. The reflective run built 19 of 235 modules; `Erdos302ReflectiveChainData07FC` (module 20) reported `failed to create thread` and exited by SIGABRT. The ledger run reached target 2999/2999, reported the same error, and Lean exited 134. Neither run reached the final axiom audit. Both had `LEAN_NUM_THREADS=1`; reflective used `lean -j 1` and a 10 GiB per-process address-space limit, ledger used Lake and 24,000,000 KiB per-process. The two runs are separate hosted jobs, not concurrent processes on one runner.

The pinned Lean v4.33.0-rc1 source `src/runtime/thread.cpp` uses `pthread_attr_setstacksize` followed by `pthread_create`, discards its return code, and maps any failure to that generic message. Its non-Emscripten default thread stack is 1 GiB unless overridden at build time; actual binary compile-time settings were not measured. `LEAN_STACK_SIZE_KB` changes it, plus a 128 KiB guard buffer, while a Lean `--tstack` flag overrides the environment. The pinned `src/runtime/object.cpp` has dedicated workers beyond the standard worker pool and can temporarily increase the standard pool while a worker blocks; `src/util/shell.cpp` also runs the shell in a thread. Thus one configured worker is not a one-thread process; Lake and Lean are separate processes. See:

- https://github.com/leanprover/lean4/blob/v4.33.0-rc1/src/runtime/thread.cpp
- https://github.com/leanprover/lean4/blob/v4.33.0-rc1/src/runtime/thread.h
- https://github.com/leanprover/lean4/blob/v4.33.0-rc1/src/runtime/object.cpp
- https://github.com/leanprover/lean4/blob/v4.33.0-rc1/src/util/shell.cpp

Hypothesis, not diagnosis: virtual-address headroom is a credible common bottleneck under the retained per-process caps, with large stack reservations multiplying thread costs; actual thread count, mappings, compile-time stack size, and `pthread_create` errno were not recorded. PID/task limits, physical/commit pressure, and other failures remain alternatives. The failures alone do not distinguish them. Test the hypothesis with the JSONL samples: compare Lean VmSize/VmPeak to its own RLIMIT_AS and Threads, and cgroup pids/memory events and limits. One-second samples may miss transient spikes; counters may be absent under cgroup v1 or unusual mounts. Neither an unchanged `memory.events` nor a sparse sample proves no memory failure. `pthread_create` errno is not available from this instrument and would need a separate controlled trace.

Candidate: `LEAN_STACK_SIZE_KB=262144` (256 MiB plus Lean's buffer) in these two workflows only. This is a measured experiment, not a proven fix; it reduces per-thread reservation while preserving both caps, timeouts, Lean versions, proofs and axiom gates. Smaller stacks may produce genuine Lean stack-overflow failures or expose other limits. Compare against an otherwise identical default-stack run with the same instrumentation; a successful run alone is not proof of causation. Artifacts include one-second, best-effort process and cgroup samples; monitor errors are nonfatal and empty/missing samples are not evidence of health.
